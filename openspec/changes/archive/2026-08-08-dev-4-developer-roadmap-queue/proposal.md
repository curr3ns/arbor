## Why

R1 redefined a checked roadmap box to mean "implemented, gated, and merged," R2 deleted `arbor-auto-refine`, and R3 taught `arbor-auto-work` to flip the box inside its own work commit. That leaves `arbor-auto-developer` — the scheduled burn-down agent — driving off a GitHub issue backlog that nothing files any more, self-seeding from a skill that no longer exists, and merging into an integration branch behind a running PR. With the checkbox meaning "implemented" and refine gone, `docs/roadmaps/*.md` is already an ordered, deduped, human-authored backlog; a second queue in GitHub adds bookkeeping without adding information. This is roadmap item R4 of `docs/roadmaps/roadmap-native-workcycles.md`.

## What Changes

- **BREAKING** Rewrite `.claude/skills/arbor-auto-developer/SKILL.md` so the roadmap files are the work queue. **Removed entirely**: the `agent:backlog` issue queue, every label requirement (`priority:*`, `type:*`), the queue cap, the `gh auth` setup step, the integration-branch setup step, the running PR and its "at most one open PR" guardrail, the whole P0/P1 PR-feedback path (review threads, `gh pr checks`, thread replies/resolution), and refine self-seeding. No occurrence of the string `arbor-auto-refine` survives anywhere in the file, frontmatter description included.
- **Selection becomes a roadmap walk.** Each cycle reads non-archived `docs/roadmaps/*.md` on `main` — explicitly excluding `docs/roadmaps/archive/` — walks roadmaps in filename order, and within the first roadmap that holds an eligible item picks the earliest incomplete phase and that phase's first unchecked item not carrying a blocked annotation. Two consequences are stated explicitly because they are exactly where a plausible reading goes wrong: a roadmap whose only unchecked items are all blocked-annotated holds no eligible item, so the walk moves on to the next roadmap by filename; and an earliest-incomplete-phase whose unchecked items are all blocked does **not** fall through to a later phase in the same roadmap — phases are strictly sequential — so that roadmap yields nothing and the walk continues to the next file.
- **Dispatch becomes one `arbor-auto-work` subagent** run autonomously (its default — no `--interaction`, no `--pr`) with the item's text and its `roadmap:docs/roadmaps/<slug>.md#R<n>` reference, merging to `main`. The subagent returns the compact result `{ outcome, work_id, branch, note }`.
- **Idle is quiet.** No eligible item anywhere — and equally, no roadmap file at all — ends the run with no dispatch, no notification, and no error. Nothing to do until the next scheduled tick.
- **Blocked bookkeeping replaces the issue comment.** On gate failure one retry subagent runs with the failure output; if that also fails, an `<!-- blocked: <reason> -->` annotation is appended to the end of the item's line and pushed to `main`, so later cycles skip it and one bad item cannot stall the roadmap. Never a third attempt on the same item in the same run.
- **The blocked push is race-aware.** This is the one case where the skill writes to a roadmap file, and `main` may have moved under it. The skill must fetch/rebase (or re-pull) and re-apply the annotation onto the current `main`, re-locating the item's line by its `**R<n>**` marker rather than by line number, and re-check that the item is still unchecked and still unannotated before re-pushing; if the item has since been checked or already annotated by another actor, the annotation is dropped rather than force-pushed.
- **Notifications fire on exactly three events**: merge landed, item blocked after retry, and roadmap complete. Roadmap complete means the merged item was the last unchecked one in its file; `arbor-auto-work` performs the archival `git mv` into `docs/roadmaps/archive/` inside its own work commit, so this skill only observes and notifies and never moves the file. No notification on dispatch and none on a quiet idle run. A missing `PushNotification` never fails the run.
- **What survives is the shape**: a scheduled (~hourly; the schedule skill's cron has a 1h minimum interval), single-cycle, one-subagent-at-a-time burn-down loop that does not loop internally; the "You MUST create a todo per step and complete them in order" directive on the cycle; the phases-are-strictly-sequential guardrail; the one-subagent-in-flight guardrail; and the "only ever touch this repo, under the maintainer's own identity" guardrail.
- **The skill still never authors roadmap content** — no writing items, no phases, no checkbox flips (the flip belongs to `arbor-auto-work` inside its work commit), and it never invokes `arbor-auto-roadmap`. The blocked annotation is bookkeeping, not authorship, and the text says so in those terms.
- **Setup**: the `gh auth` step and the integration-branch step both go. What remains must be true of a roadmap-driven, merge-to-`main` skill; if nothing meaningful remains, the section is dropped.
- Rewrite the YAML frontmatter `description` — it currently describes the PR-feedback path, the issue backlog, and refine self-seeding, all of which are being removed — and bump `metadata.version` from `1.4` to `2.0`, because this is a rewrite rather than an increment.

## Capabilities

### New Capabilities
- `roadmap-queue`: The `arbor-auto-developer` skill's contract as a roadmap-driven burn-down loop — what a cycle reads, how it selects an item across roadmaps and phases, how it dispatches exactly one `arbor-auto-work` subagent, how it handles idle, failure, retry, and the blocked annotation with its push race, when it notifies, and the guardrails that bound it. Also carries this change's scope fence.

### Modified Capabilities
- `work-cycle`: One requirement is retired. **Change scope is limited to the work-cycle skill** was written by `dev-3-workcycle-roadmap-close` to fence that change's blast radius, and it states that `arbor-auto-developer` SHALL NOT be modified. That fence has served its purpose and is directly contradicted by this change, which modifies exactly that file. It is removed and replaced by this change's own scope requirement in `roadmap-queue`. This is spec bookkeeping only: no file under `.claude/skills/arbor-auto-work/` changes and no behavior of `arbor-auto-work` changes.

## Impact

- **Files changed**: `.claude/skills/arbor-auto-developer/SKILL.md` only, plus these OpenSpec artifacts. `git status --porcelain` must list nothing outside that one path and `openspec/`.
- **Explicitly out of scope (the change is invalid if violated)**: `.claude/skills/arbor-auto-work/`, `.claude/skills/arbor-auto-roadmap/`, `.claude/skills/arbor-opsx-auto/`, and `.claude/skills/arbor-project-scaffold/` are **not** modified, moved, or deleted, and **no new skill directory is created**.
- **`--goal` is not added here.** The foreground mode is roadmap item R5, shipping immediately after this one and extending what is written here. This skill's default stays **one cycle per invocation**, so nothing written now may presuppose or half-implement a loop mode.
- **`docs/roadmaps/roadmap-native-workcycles.md` is not modified.** R4's own checkbox is flipped outside this change, by `arbor-auto-work`'s commit step.
- **`docs/roadmaps/archive/` is not created here**, with or without a `.gitkeep`. R6 owns scaffolding it, and `arbor-auto-work` creates it on demand at the moment of first archival.
- **Consumer/producer state after this change**: `arbor-auto-roadmap` (R1) produces the roadmap and defines the `docs/roadmaps/<slug>.md#R<n>` reference format; `arbor-auto-work` (R3) consumes the reference, flips the box, and archives a completed roadmap inside its work commit. This change makes `arbor-auto-developer` the first automated producer of that token, closing the loop the roadmap describes: roadmap plans, developer burns down, work builds and marks done, `arbor-opsx-auto` runs the lifecycle underneath.
- **Behavioral consequence for operators**: autonomous merges now land on `main` rather than on an integration branch behind a human-reviewed PR. That is the roadmap's intent — the gate inside `arbor-auto-work` is the quality boundary — but it is a real change in blast radius and the skill's own guardrails are what bound it.
- **Verification**: this is a skills repo — the product is Markdown skill definitions under `.claude/skills/<name>/SKILL.md`. There is no build, no test suite, no `package.json`, and no gate command. Verification is reading the edited Markdown against every acceptance criterion literally, plus the concrete greppable checks attached to each task.
- **Known pre-existing condition**: `openspec validate --all` reports "Spec must have a Purpose section" against the specs already in `openspec/specs/`. That predates this change, is out of scope, and is not addressed here; the delta specs added here follow the same structure as the archived changes that produced those specs.
- **Change directory name**: the OpenSpec CLI (v1.2.0) rejects an uppercase change name, so the directory is `openspec/changes/dev-4-developer-roadmap-queue/`, matching the lowercase convention of the three archived changes. The work ID remains `DEV-4-developer-roadmap-queue`.
