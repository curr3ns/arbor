## Why

R4 rewrote `arbor-auto-developer` into a roadmap-driven burn-down agent whose every run is exactly one cycle — read the roadmaps, work one item, exit — with the `schedule` skill's cron (1h minimum interval) supplying the "keep polling". That is the right shape for unattended burn-down and the wrong shape for a human sitting down to watch a roadmap finish: at one item per hour there is no path from "roadmap written" to "roadmap archived" in a single sitting, and the parent roadmap explicitly rules out a fourth skill to provide one. `/goal` already provides exactly the missing primitive — a session-scoped Stop hook that keeps a session going until a stated condition holds and then clears itself — so the foreground mode folds into this skill as a flag rather than a new skill. This is roadmap item R5 of `docs/roadmaps/roadmap-native-workcycles.md`.

## What Changes

- **Add a `--goal` foreground mode** to `.claude/skills/arbor-auto-developer/SKILL.md`. Invoking the skill with `--goal` sets a session-scoped goal via `/goal` whose condition names the target roadmap, literally of the form "Every item in `docs/roadmaps/<slug>.md` is checked off and the file has been migrated to `docs/roadmaps/archive/`", and then works items **one at a time** — the same single-item cycle R4 specifies, repeated — relying on the Stop hook to keep the session going and to auto-clear when the condition holds.
- **Make the two modes legible as a contrast, not a flag in a list.** A short mode framing lands near the top of the file and a dedicated `## Foreground goal mode (--goal)` section carries the behavior. The scheduled path is unattended, cron-paced, and one cycle per tick; the goal path is foreground, human-invoked, and runs to a stated finish line. Burying `--goal` in an options list would make an agent reading the file treat them as interchangeable, which they are not.
- **The default is unchanged: one cycle per invocation.** Without `--goal` the skill behaves exactly as R4 specified — read, select one, dispatch one, exit — so the scheduled path is untouched. The cron invocation never passes `--goal`.
- **Document `/goal`'s preconditions and the fallback.** `/goal` requires a trusted workspace and unrestricted hooks; it is unavailable when `disableAllHooks` or `allowManagedHooksOnly` is set in settings or by policy, and Stop hooks are REPL-only, so a non-REPL invocation cannot have one either. When `/goal` is unavailable for any of these reasons, the skill **reports the reason** and **falls back to running cycles back-to-back in-session** until no eligible item remains in the target roadmap.
- **Both paths terminate on the same condition** — no eligible item remains in the target roadmap — and the file states why the loop cannot livelock: every iteration either merges an item (one fewer unchecked item) or exhausts an item's two-attempt budget and annotates it blocked (one fewer *eligible* item), both strictly decreasing on a finite set. A roadmap whose every unchecked item carries a `<!-- blocked: ... -->` annotation therefore yields no eligible item, and that is a **terminating state, not a retry state**. Because the `/goal` condition can never hold in that state, the skill issues `/goal clear` itself before stopping rather than leaving the Stop hook re-prompting an empty session forever.
- **Re-read the per-run attempt budget under a loop.** R4's guardrail "at most two attempts per item per run" was written when a run was one item. Under `--goal` a run spans many items, so the file states the budget's operative reading explicitly: it is **per item** — one original plus one retry — and an item that exhausts it is annotated blocked and is thereafter skipped by the walk, so no item ever gets a third attempt in a goal run either. That per-item reading is precisely what makes the loop terminate. The companion rule "never move on to a different item in its place" is likewise clarified as a **within-cycle** rule: a failed cycle never chains into another item; the goal loop reaches the next item by starting a new cycle whose walk re-reads `main`, not by continuing a failed one.
- **The one-subagent-at-a-time guardrail holds inside the loop.** "Works items one at a time" means the same single dispatch per cycle, repeated — never two subagents in flight, never a batch, and a retry still only follows a finished attempt. Autonomy is also unchanged: "foreground" describes the human watching the session, not approval prompts, so dispatched subagents still run `arbor-auto-work` in its default autonomous mode with no `--interaction` and no `--pr`.
- **One goal run targets one roadmap, chosen deterministically.** `--goal` takes an optional roadmap argument (a slug or a `docs/roadmaps/<slug>.md` path); with no argument the target is the first roadmap holding an eligible item under the skill's existing filename-order walk. The target is resolved **once**, at the start of the run, and pinned — the `/goal` condition names one `<slug>` and must not drift away from it. When the target finishes while other roadmaps still hold eligible items, the run ends with the condition met and reports the remaining roadmaps plus the invocation to continue with the next one; it does not roll onto another roadmap inside the same goal run.
- Update the YAML frontmatter `description` to mention the new mode, and bump `metadata.version` from `"2.0"` to `"2.1"` — this adds a mode on top of R4's structure rather than replacing it.

## Capabilities

### New Capabilities

None. This change extends the existing `roadmap-queue` capability rather than introducing a new one; a separate capability for one flag on one skill would split a single skill's contract across two spec files.

### Modified Capabilities

- `roadmap-queue`: The `arbor-auto-developer` contract gains the foreground goal mode. **Added**: the mode framing and its default; the `/goal` condition form and the session-scoped Stop hook mechanism; deterministic, pinned target-roadmap selection; the one-item-at-a-time loop with the one-subagent guardrail intact; the termination argument and the `/goal clear` on the all-blocked terminal state; the per-item reading of the two-attempt budget; `/goal`'s preconditions, the named unavailability settings, and the report-and-fall-back path; the completion handoff when other roadmaps remain; the statement that no notification event is added; and the frontmatter/version requirement. **Removed**: **The foreground goal mode is not added by this change**, R4's forward-looking fence, which is directly contradicted by this change and would otherwise leave the live spec asserting that the mode does not exist alongside the requirements that specify it. Its still-true scenario "Default remains one cycle" survives under the new mode requirement. **Modified**: **Change scope is limited to the auto-developer skill**, rewritten as this change's own blast-radius fence rather than left as R4's.

## Impact

- **Files changed**: `.claude/skills/arbor-auto-developer/SKILL.md` only, plus these OpenSpec artifacts. `git status --porcelain` must list nothing outside that one path and `openspec/`.
- **Explicitly out of scope (the change is invalid if violated)**: `.claude/skills/arbor-auto-work/`, `.claude/skills/arbor-auto-roadmap/`, `.claude/skills/arbor-opsx-auto/`, and `.claude/skills/arbor-project-scaffold/` are **not** modified, moved, or deleted, and **no new skill directory is created**.
- **R4 is not re-litigated.** The roadmap-queue walk, the archive exclusion, the phases-are-strictly-sequential rule, the dispatch contract and its `{ outcome, work_id, branch, note }` return, the retry-then-blocked-annotation path with its push race, the three-event notification set, the roadmap-completion observation, the never-author-roadmap-content guardrails, and the merge-to-`main` target are all settled and correct. This change **adds a mode on top of them**; it must not rewrite, soften, or contradict any of them, and it adds no fourth notification event.
- **`docs/roadmaps/roadmap-native-workcycles.md` is not modified.** R5's own checkbox is flipped outside this change, by `arbor-auto-work`'s commit step in the work cycle that carries it.
- **`docs/roadmaps/archive/` is not created here**, with or without a `.gitkeep`. R6 owns scaffolding it, and `arbor-auto-work` creates it on demand at the moment of first archival.
- **Environment facts this change is built on** (verified against the installed Claude Code binary, and not to be contradicted): `/goal <condition>` sets a session-scoped Stop hook and confirms with "A session-scoped Stop hook is now active with condition: …"; `/goal clear` stops early and `/goal active` shows the current goal; the trusted-workspace failure reads "/goal is only available in trusted workspaces. Restart, accept the trust dialog, and try again."; the restricted-hooks failure reads "/goal can't run while hooks are restricted (disableAllHooks or allowManagedHooksOnly is set in settings or by policy)."; and Stop hooks are REPL-only ("Prompt stop hooks are not yet supported outside REPL"), which is a further legitimate reason the fallback path exists.
- **Behavioral consequence for operators**: a `--goal` run can land many autonomous merges on `main` in one sitting, where a scheduled run lands at most one per tick. The blast radius per merge is unchanged — the gate inside `arbor-auto-work` is still the quality boundary and one subagent still runs at a time — but the rate is not, and the mode is human-invoked precisely so that a human is present while it happens.
- **Verification**: this is a skills repo — the product is Markdown skill definitions under `.claude/skills/<name>/SKILL.md`. There is no build, no test suite, no `package.json`, and no gate command. Verification is reading the edited Markdown against every acceptance criterion literally, plus the concrete greppable checks attached to each task in `tasks.md`, which is this change's real verification instrument.
- **Known pre-existing condition**: `openspec validate --all` reports "Spec must have a Purpose section" against specs already in `openspec/specs/`. That predates this change, is out of scope, and is not addressed here. `openspec validate dev-5-developer-goal-mode --strict` is the check that applies to this change's own artifacts.
- **Change directory name**: the OpenSpec CLI rejects an uppercase change name, so the directory is `openspec/changes/dev-5-developer-goal-mode/`, matching the lowercase convention of the archived changes. The work ID remains `DEV-5-developer-goal-mode`.
